# CheckStock — где сейчас товар

Веб-прототип складского учёта для одного магазина: остатки по артикулам и складам фулфилмента (ФФ),
резервы FBS, перемещения между ФФ, поставки FBO и история операций.

Стек: Python 3.11, FastAPI, SQLAlchemy 2, PostgreSQL 16, серверные страницы на Jinja2 (без сборки фронтенда).

## Запуск

Нужен только Docker.

```bash
docker compose up --build
```

Откройте http://localhost:8000. При первом старте создаются таблицы и тестовые данные из задания:
ФФ «Север» и «Юг», три артикула и тестовый приход (он виден в истории операций).

- Порт занят: `APP_PORT=8080 docker compose up --build`.
- Начать с чистой базы: `docker compose down -v`, затем снова `up`.

## Проверка

### Автотесты

```bash
docker compose run --rm app pytest
```

23 теста идут на настоящем PostgreSQL (отдельная база `checkstock_test`, данные приложения не трогаются).
Они покрывают складские сценарии из задания: учёт после каждого действия, нехватку, удаление ФФ с остатком,
повторные и одновременные подтверждения. После шагов сценария тест проигрывает журнал операций с нуля
и сверяет результат с таблицей остатков.

### Руками, за пять минут

Стартовые остатки: SKU-101 — Север 10, Юг 6; SKU-102 — Север 5; SKU-103 — Юг 4.

| № | Действие | Что должно получиться |
|---|----------|-----------------------|
| 1 | Резерв FBS: SKU-101, Юг, 8 шт. | Отказ: на Юге доступно 6, подсказка «на Севере — 10». Остатки не изменились |
| 2 | Резерв FBS: SKU-101, Север, 4 шт. | Север: физически 10, резерв 4, доступно 6 |
| 3 | Перемещение: SKU-101, Север → Юг, 7 шт. | Отказ: 4 шт. под резервом, доступно только 6 |
| 4 | Перемещение: SKU-102, Север → Юг, 3 шт. | Север 2, Юг 0, «в пути между ФФ» 3 |
| 5 | «Принять на ФФ» у перемещения | Юг 3, в пути 0 |
| 6 | «Отправить клиенту» у заказа FBS | Север: физически 6, резерв 0; «FBS → клиент» 4 |
| 7 | Отправка FBO: SKU-103, Юг, 2 шт. | Юг 2, «FBO → склад МП» 2 — до нажатия «Принято складом МП» |
| 8 | Откройте страницу в двух вкладках и подтвердите один документ в обеих | Во второй вкладке — «уже принят, повторно товар не зачислен» |
| 9 | Склады ФФ → удалить «Юг» | Остаток числится на «Юг (удалён)», столбец остался на экране остатков, история цела |
| 10 | Приход или резерв на удалённом «Юге» | Отказ. Перемещение Юг → Север проходит — так остаток вывозится |

Блок «Сверка» под таблицей остатков после каждого шага должен показывать «да» по всем артикулам.

## Как устроен учёт

Три таблицы на три разных вопроса:

- **`stock`** — «сколько сейчас»: по строке на пару артикул × ФФ, поля `on_hand` (физически) и `reserved` (резерв FBS).
  «Доступно» не хранится, а считается как `on_hand − reserved`, поэтому разойтись с остатком не может.
- **`shipments`** — «что в работе»: документы перемещений, заказов FBS и поставок FBO со статусом
  (`reserved` → `in_transit` → `done`, для FBS ещё `cancelled`). Товар «в пути» — это сумма документов в статусе `in_transit`.
- **`operations`** — «что происходило»: журнал, в который строки только добавляются. Это история операций.

Товар в пути намеренно не числится ни на одном складе: отправленное перемещение сразу уменьшает остаток
отправителя, а получателю зачисляется только при приёмке. Так «доступно» никогда не включает то, чего на полке ещё нет.

| Действие | Физически | Резерв | Документ |
|----------|-----------|--------|----------|
| Приход | + на ФФ | | |
| Отправка перемещения | − на отправителе | | в пути |
| Приёмка перемещения | + на получателе | | принят |
| Резерв FBS | | + | в резерве |
| Отмена резерва | | − | отменён |
| Отправка заказа FBS | − | − | в пути к клиенту |
| Отправка FBO | − | | в пути на склад МП |
| Приёмка FBO / доставка FBS | | | принят |

## Ключевые решения

**Остатки сходятся после каждого действия.** Каждая операция — одна транзакция: блокировка строки остатка
(`SELECT … FOR UPDATE`), проверка, изменение и запись в журнал либо проходят вместе, либо не проходят совсем.
В базе стоят `CHECK`-ограничения `on_hand >= 0` и `0 <= reserved <= on_hand` — даже при ошибке в коде
PostgreSQL не даст уйти в минус. На экране остатков есть сверка: принято всего = на ФФ + в пути + принято
маркетплейсом + доставлено клиентам.

**Повторное подтверждение не списывает дважды.** Защита двух видов, потому что повторы бывают разные:

- *Подтверждение документа* (отправить, принять, отменить). Строка документа блокируется, и переход выполняется
  только из нужного статуса. Второй клик или второй менеджер увидят «уже отправлен» — остатки не тронуты.
- *Повторная отправка формы* (двойной клик, «назад» и повтор в браузере). У каждой формы создания одноразовый
  ключ `request_id`; в журнале на нём уникальный индекс. Запрос с уже использованным ключом ничего не делает.
  Одновременные запросы с одним ключом выстраиваются через `pg_advisory_xact_lock`.

После каждого POST идёт редирект (Post/Redirect/Get), так что обновление страницы форму не повторяет.

**Нехватка на выбранном ФФ.** Система не списывает молча с другого склада: откуда везти — решение менеджера,
от него зависят сроки и стоимость. Операция отклоняется целиком, а в сообщении видно, сколько доступно на
выбранном ФФ (с разбивкой на физический остаток и резерв) и на каких ФФ товар есть. Дальше менеджер выбирает
другой ФФ или сначала оформляет перемещение. Если не хватает и по всем складам — сообщение говорит об этом прямо.

**Удаление ФФ — мягкое.** У склада проставляется `deleted_at`, строки остатков и истории продолжают на него
ссылаться. Что это значит на практике:

- товар по-прежнему числится на удалённом ФФ, столбец «ФФ … (удалён)» остаётся на экране остатков, пока там что-то лежит;
- начать новое нельзя: приход, резерв, FBO и входящие перемещения отклоняются;
- закончить начатое можно: отправить или отменить резерв, принять перемещение, которое уже в пути
  (товар физически приехал и должен где-то числиться);
- остаток вывозится перемещением на действующий ФФ.

Запретить удаление склада с остатком было бы проще, но в задании прямо сказано сохранить остатки и историю.

**Переименование ФФ** меняет только имя: остатки и история привязаны к `id`, поэтому в истории склад
показывается под актуальным названием. Имя уникально среди действующих ФФ (частичный уникальный индекс),
удалённый склад не мешает завести новый с тем же именем.

**Правила учёта в одном месте.** Весь код, меняющий остатки, — в `app/services.py`. Маршруты FastAPI только
принимают форму и показывают результат, тесты вызывают те же функции напрямую.

## Структура

```
app/
  main.py        маршруты FastAPI: три страницы и обработчики форм
  services.py    складские операции и все правила учёта
  queries.py     выборки для экранов: остатки, документы в работе, история
  models.py      таблицы и ограничения
  seed.py        тестовые данные из задания
  db.py          подключение к PostgreSQL
  templates/     страницы Jinja2
  static/        стили
tests/           складские сценарии на настоящем PostgreSQL
```

## Что упрощено

- Один магазин — отдельной таблицы магазинов нет. Товары заводятся тестовыми данными, справочника в интерфейсе нет.
- Нет авторизации и ролей.
- Таблицы создаются при старте (`create_all`); в рабочем проекте были бы миграции Alembic.
- Маркетплейс и клиент — конечные точки без собственного учёта: приёмка FBO и доставка FBS просто закрывают документ.
- Сообщения об успехе и ошибке передаются через адресную строку после редиректа — без сессий.
